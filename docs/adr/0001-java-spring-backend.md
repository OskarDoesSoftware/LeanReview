# Migrate the backend to Java and Spring Boot while retaining React

The user chose Java, Spring Boot, Spring Data JPA, and SQLite because this is the stack they are most comfortable building and maintaining; React remains the frontend. This supersedes the Node/Express and prepared-SQL-only technology defaults in issues [5](https://github.com/OskarDoesSoftware/LeanReview/issues/5) and [10](https://github.com/OskarDoesSoftware/LeanReview/issues/10), while preserving their product, privacy, recovery, and platform contracts. Implementation follows the staged [migration plan](https://github.com/OskarDoesSoftware/LeanReview/issues/21), with existing API/storage compatibility and a temporary Node analysis helper; no performance gain or completed migration is implied.

2026-10-15 cutover: after [platform and performance acceptance](../migration/java-launch-acceptance.md), the standard npm commands select Java and the Express runtime is retired. The original SQLite schema, captured-artifact hashes and application-data paths remain unchanged. First production startup creates a verified paired database/cache backup before migration or restart recovery. Rollback restores that pair before using the pre-cutover Node revision, `77df360`; an older runtime must never open the evolved Java data directory directly.

The bounded Node helper intentionally remains for TypeScript compiler behavior and the transitional Java Tree-sitter grammar. Its source lives under `backend-java/helper`, independent of the retired backend. Removing it is a separate decision. Frontend tooling and the Java launcher also require Node 24; they do not host another application backend. Java is slower on the recorded synthetic workloads but passes the user-approved ceilings, so maintainability remains the reason for this choice.
